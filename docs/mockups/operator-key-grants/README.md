# Editable operator key grants mockup

Interactive design proposal for [Wyrwood
#157](https://github.com/wyrd-company/wyrwood/issues/157), produced by epic task
8 for task 10 to implement after operator approval. **Operator judgement is
pending.** This artifact records no approval.

Open [index.html](index.html) directly in a browser. It is self-contained and
needs no server, build, credentials or network. The pull request also links a
hosted copy and screenshots. All displayed identities, grants and policies are
fictional fixtures. Changes live in memory until reload or **Reset demo**.

## Walk through

1. On **Operator keys**, choose **Edit grant** for `menagerie`.
2. Select `bob-secrets` under **Policies**. Change **Agents**, **Read**,
   **Bind** or **Policy write** to see **What this key can do** update.
3. Choose **Review grant**. Compare the complete old and new grant and the
   effective permission preview. **Cancel** returns to editing without applying
   anything.
4. Choose **Confirm changes**. The approved key retains its label and
   fingerprint; the updated list and **Events** reflect the change. Open
   **Events** to inspect its operator, timestamp, subject, fingerprint, and full
   before/after grant.
5. Use **Edit policy** in the prototype controls. Its **Operator keys** tab
   reflects the same grant. Select or clear `menagerie`, then **Save and
   validate**, inspect the confirmation, and confirm. Reopen the key to see the
   same Policies list.
6. Try **Create policy**. Name a policy, choose the approved keys that may bind
   it, and **Create and validate**. The confirmation includes the proposed
   policy creation and every changed key grant.

Without an edit, Events displays a clearly marked example. After confirmation it
displays the events generated by this session, newest first.

## Design decisions for review

- Keep the existing dark green sidebar, neutral canvas, white panels, green
  primary actions, IBM Plex font stack with system fallbacks, approved-key
  table, and one row of policy tabs. References: [Operator
  keys](../../user/assets/web-operator-keys.png), [Policy
  editor](../../user/assets/web-policy.png),
  [Events](../../user/assets/web-events.png), and the base frontend `style.css`.
  The stylesheet and emblem are copied into this isolated file; application
  files are untouched.
- **Edit grant** opens a focused screen for one approved key. Its identity is
  read-only. The existing grant choices and permission wording are retained.
  Confirmation is a separate page with a return path, rather than a nested
  overlay.
- **Operator keys** is a new tab on both create and edit policy screens. Both
  surfaces edit the same grant. A key's existing actions apply to the whole
  Policies list: adding a policy can also extend Read or Policy write; removing
  it removes those permissions for this policy. The warning and confirmation
  state this explicitly.
- A key without Bind cannot be selected on the policy screen. **Edit grant** is
  the explicit path to enable it. Actions are never silently enabled.
- A key with All policies already includes this policy. Its checked selection is
  disabled, with a link to narrow the grant from the key screen. This avoids
  representing an exclusion the grant cannot store.
- A confirmed change applies to the next client request, including an existing
  connection. It needs no replacement Transit key, client configuration change,
  restart or revocation.
- Each changed key gets its own event containing full old and new grants, even
  when initiated from a policy. `operator-key-grant-changed` and the event
  detail layout are proposals, not a committed API or storage design.

## Boundaries

This is a mockup, not application code or an authorization implementation. It
models local grant validation, empty/no-change feedback, cancellation, explicit
confirmation, shared in-memory state and event detail. Unrelated policy sections
and HCL editing are context only. Revoke, pending-key approval, API failures,
concurrent edits, persistence and live authentication are outside this
prototype. Task 10 must handle them in the product. The mockup does not
establish the behavior of bindings already created when a grant narrows.

The operator judges visual fit and intent through the epic orchestrator. The
mockup must not be treated as approved until that decision is linked in the task
log.

## Re-run the walkthrough

The [browser walkthrough](verify.mjs) opens the HTML from disk and checks the
connected editing flows, cancellation, event history, invalid inputs, wildcard
selection, keyboard operation, phone menu, page overflow at phone and desktop
widths, and enlarged text. It writes screenshots and a JSON report outside the
repository. The report begins as failed and changes to passed only on completion.

Use an existing Playwright installation or install it in a disposable directory,
then run:

```sh
node docs/mockups/operator-key-grants/verify.mjs /absolute/evidence-directory
```

`PLAYWRIGHT_MODULE` can name the absolute path to a Playwright or Playwright Core
module. `PLAYWRIGHT_BROWSERS_PATH` can select a disposable browser cache. Optional
`AXE_SCRIPT` names a local axe-core script; when supplied, the walkthrough also
scans the five main screens at both widths for WCAG A/AA violations and includes
the reports. No package manifest or lockfile is needed by the mockup.
